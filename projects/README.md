# Проекты: шесть сквозных задач

[← К содержанию курса](../README.md)

Лабораторные тренируют механизмы по отдельности. Проекты собирают их вместе, и здесь появляется то, чего в лабораторных нет: компромиссы. Механизмы начинают конфликтовать, бюджет ограничен, и приходится решать, что важнее.

**Отличие проекта от лабораторной.** У лабораторной один правильный ответ и автоматическая проверка. У проекта есть рубрика оценки, но реализаций много, и защита включает объяснение выбранных компромиссов. Проект без объяснения решений не считается сданным.

## Проект 1. Агент-исследователь

**Задача.** Агент отвечает на вопросы о незнакомой кодовой базе: «где обрабатывается авторизация», «какие эндпоинты меняют данные пользователя», «что произойдёт, если убрать этот параметр». Только чтение, никаких изменений.

**Что нужно построить.** Цикл с бюджетами; три инструмента (`search_code`, `read_file`, `list_dir`) с описаниями по правилам 2.3; план-файл; компакция; трейс. Ответ обязательно содержит ссылки на файлы и строки.

**Рубрика оценки.**

| Измерение | A | B | C | D |
|---|---|---|---|---|
| Точность ссылок | Все утверждения имеют `файл:строка`, проверено выборочно | Больше 80% | Больше 50% | Ссылок нет или неверны |
| Бюджет контекста | Прогон на 20 шагов не растёт линейно, компакция работает | Компакция есть, потерь нет | Компакция есть, решения теряются | Компакции нет |
| Честность | Есть ответы «не нашёл» там, где нечего найти | Иногда | Редко | Всегда отвечает |
| Диагностируемость | По `run_id` восстанавливается путь за минуту | За 5 минут | С трудом | Невозможно |

**Готово, когда.** 15 вопросов по незнакомому проекту (возьмите любой открытый репозиторий на 5–20 тысяч строк), из них 3 — с ответом «в коде этого нет». Проходят 12 из 15, все 3 «нет» — честные отказы, средняя стоимость известна.

**Ниже B не принимается ни по одному измерению.** Это правило для всех проектов.

## Проект 2. Агент-редактор кода

**Задача.** Агент исправляет падающий тест в реальном репозитории, не меняя тесты и не ломая остальное.

**Что нужно построить.** Всё из проекта 1, плюс: инструменты записи с классификацией опасности; песочница с `git worktree`; постусловие из конъюнкции четырёх условий; `BACKLOG.md` для «заодно»; golden set из 20 задач.

**Компромисс, который придётся решать.** Чем строже проверки, тем меньше задач агент закрывает, но тем надёжнее результат. Найдите точку и обоснуйте её числами: покажите pass rate при трёх разных наборах постусловий.

**Готово, когда.** 20 задач в golden set (реальные баги из истории проекта — `git log` ваш друг), pass rate измерен с интервалом, доля прогонов, изменивших `tests/`, равна нулю (это `reject`-условие), откат любого прогона — одна команда.

**Обязательный артефакт.** Отчёт: три конфигурации постусловий, для каждой pass rate с интервалом и число ложных «успехов», найденных при ручной проверке 10 случаев.

## Проект 3. Агент в проде

**Задача.** Довести агента из проекта 1 или 2 до состояния, в котором его можно выкатить: с SLO, канарейкой, откатом, дашбордом и бюджетами.

**Что нужно построить.** Манифест релиза; промпты в файлах с версиями и `CHANGELOG`; конвейер из пяти ворот; канарейка с правилами автоотката; пять графиков; алерты; уровни деградации; учёт расходов по осям.

**Компромисс.** Полный конвейер выката занимает час и стоит около доллара. Соблазн срезать ворота велик. Задача — показать на числах, что срезание ворот дороже: возьмите три реальных изменения промпта, прогоните через ворота и покажите, сколько из них не прошли бы (обычно одно из трёх).

**Готово, когда.** Откат занимает меньше минуты (замерено секундомером); канарейка автоматически откатилась на подставном ухудшении (внесите регрессию специально); дашборд отвечает на три вопроса из 10.2; `cost_per_success` известен и ограничен сверху.

**Обязательный артефакт.** Учения: журнал трёх откатов с временем каждого.

## Проект 4. Агент поддержки с RAG

**Задача.** Агент отвечает на вопросы пользователей по документации продукта, с обязательными ссылками и честным «не нашёл».

**Что нужно построить.** Индексация с иерархическим чанкингом; гибридный поиск с RRF; реранк с порогом отсечения; цитирование с машинной проверкой покрытия; набор оценки на 80 вопросов, включая 15% `no_answer`; защита от инъекций через документы.

**Компромисс, который здесь главный.** Порог отсечения. Низкий порог — больше ответов и больше выдумок. Высокий — честнее, но пользователи слышат «не нашёл» на вопросы, ответ на которые есть. Задача — построить кривую: доля правильных ответов и доля ложных отказов в зависимости от порога, и выбрать точку с обоснованием.

**Готово, когда.** recall@30 выше 0,90, recall@6 выше 0,80; faithfulness выше 0,95; на 12 вопросах `no_answer` система честно молчит минимум в 11; `check_citations` не пропускает утверждений без источника; набор инъекций через документы не приводит к опасным действиям.

**Обязательный артефакт.** График «порог отсечения против качества» с отмеченной выбранной точкой и объяснением выбора.

## Проект 5. Мульти-агентный конвейер

**Задача.** Взять задачу, которую одиночный агент решает плохо из-за объёма контекста, и показать числами, что мульти-агентная схема решает её лучше — либо честно показать, что не решает.

**Пример задачи.** «Найди, какой из шести сервисов вызывает рост p95, и предложи исправление» с логами и кодом на сотни тысяч токенов.

**Что нужно построить.** Честная базовая линия (одиночный агент со всем из модулей 01–04); супервизор с собственной логикой (проверка, повтор, поиск конфликтов); подагенты-исследователи с жёстким лимитом объёма ответа; `SubTask` и `SubResult` как структуры; корреляция трейсов; сравнение по протоколу 7.9.

**Компромисс.** Налог на оркестрацию против изоляции контекста. Ваша задача — не «доказать, что мульти-агент лучше», а измерить. Отрицательный результат («на нашей задаче мульти-агент дороже и не точнее») — полноценная сдача проекта, если он получен корректно.

**Готово, когда.** 20 задач, по 5 прогонов на каждую конфигурацию; таблица сравнения по pass rate, `cost_per_success`, p95 латентности, доле конфликтов; вывод с обоснованием; дерево прогонов восстанавливается по `trace_id`.

**Обязательный артефакт.** Отчёт на две страницы с решением «использовать или нет» и числами, на которых оно основано.

## Проект 6. Автономный ночной прогон

**Задача.** Агент работает 6–8 часов без человека и утром оставляет отчёт, которому можно верить.

**Что нужно построить.** Всё из предыдущих проектов, плюс: чекпоинты каждые 5–8 шагов; двухфазное подтверждение (пакет ожидающих подтверждений вместо блокировки); безопасное завершение с обработкой сигналов; `handoff.md` и `resume()` со сверкой состояния; классификатор отказов; уровни деградации по бюджету; ограничение радиуса поражения по пяти вопросам из 8.2.

**Компромисс.** Чем автономнее прогон, тем больше должен быть радиус поражения — иначе агент будет постоянно упираться в границы. Задача — найти набор прав, при котором прогон продуктивен, а худший сценарий приемлем. Это решение оформляется письменно, до запуска.

**Готово, когда.** Прогон отработал минимум три ночи подряд; ни одна ночь не закончилась зависанием (все прогоны имеют `run.finish`); доля `resumable` среди незавершённых выше 80%; утренний отчёт содержит все шесть элементов из 14.7; ни одного необратимого действия без подтверждения; известна стоимость ночи.

**Обязательные артефакты.** Ответы на пять вопросов о радиусе поражения (до запуска). Три утренних отчёта. Разбор минимум одного отказа с добавленной задачей в golden set.

## Общие требования ко всем проектам

**Репозиторий, а не блокнот.** Проект — это git-репозиторий с `README.md`, `Makefile`, тестами и `.env.example`. Ноутбуки не принимаются: агент — это система, а не эксперимент.

**`make doctor` на чистой машине.** Проект должен разворачиваться и запускаться по инструкции из `README` без вашего участия. Проверьте это на самом деле, а не в уме.

**Числа, а не впечатления.** Любое утверждение о качестве, стоимости или скорости сопровождается способом получения числа. «Работает быстро» — не утверждение; «p95 = 6,2 с на 100 прогонах» — утверждение.

**Отчёт о компромиссах.** Одна страница: какие три решения были неочевидны, какие альтернативы рассматривались, по каким числам выбрали. Это самая ценная часть сдачи и то, что отличает инженера от исполнителя.

**Чек-листы перед сдачей.** [before-first-run.md](../checklists/before-first-run.md) для всех проектов, [before-prod.md](../checklists/before-prod.md) для проектов 3 и 6.

## Как оценивать себя

Каждый проект оценивается по четырём измерениям, шкала A/B/C/D, ниже B не принимается.

| Измерение | Что проверяется |
|---|---|
| Работает | Критерии «готово, когда» выполнены и проверяемы командой |
| Измеримо | Есть golden set, метрики с интервалами, базовая линия в файле |
| Безопасно | Границы, права, песочница, подтверждения — по чек-листу |
| Понятно | По трейсу восстанавливается любой прогон; отчёт о компромиссах написан |

**Типичная ошибка при самооценке.** Ставить A за «работает» и не замечать D за «измеримо». Работающий агент без эвалов — это прототип, а не результат: вы не сможете его улучшать и не заметите деградации.
