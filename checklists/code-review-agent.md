# Чек-лист: ревью изменений в агенте

[← Все чек-листы](README.md) · Время: 15 минут

Обычное ревью кода проверяет корректность. В агенте этого мало: изменение одной строки в промпте или одного слова в описании инструмента меняет поведение системы сильнее, чем рефакторинг на сто строк. Этот список — про то, что специфично для агентов.

**Главный вопрос ревьюера, к которому сводится всё остальное:** *какое поведение это меняет и какой тест это поймает?*

---

## 1. Что вообще изменилось

- [ ] Понятно из описания пулл-реквеста, какое поведение меняется, а не только что меняется в коде
- [ ] Если менялся промпт — приложены числа эвалов до и после
- [ ] Если менялось описание инструмента — приложен результат теста описаний
- [ ] Если менялась политика прав — видно, права сужаются или расширяются
- [ ] Изменение затрагивает один слой; смешанные изменения (промпт плюс политика плюс инструменты) стоит разделить

## 2. Промпты

- [ ] Промпт лежит в `prompts/vN/`, а не в строковой константе в коде
- [ ] Версия внутри файла обновлена
- [ ] `CHANGELOG.md` дополнен: изменение, причина, измеренный эффект
- [ ] Критичные правила и запреты находятся в первых строках, а не в середине
- [ ] Если правило переехало ниже — есть исполняемый эквивалент в политике
- [ ] Изменение не добавило дату, идентификатор или что-то изменчивое в начало (иначе ломается кэш)
- [ ] Ничего не удалено «как ненужное» без проверки эвалами

## 3. Инструменты

- [ ] Новый инструмент имеет описание по [десяти правилам 2.3](../02-tool-calling/#23-описание-инструмента--это-интерфейс-и-его-читает-модель), включая «когда НЕ использовать» и пример
- [ ] У всех параметров есть `description`; категориальные — через `enum`
- [ ] На объектах схемы стоит `additionalProperties: false`
- [ ] У числовых параметров есть `minimum` и `maximum`
- [ ] Инструмент классифицирован по опасности A–E; классы C–E внесены в `DANGEROUS.md`
- [ ] Ни одно исключение не выходит из инструмента наружу
- [ ] `error_code` — из закрытого списка; `hint` содержит действие и короче 200 символов
- [ ] Есть таймаут; вывод обрезается с флагом
- [ ] Неидемпотентная операция защищена ключом
- [ ] Инструмент не имеет скрытого состояния между вызовами

## 4. Политика и права

- [ ] Расширение прав — отдельный пулл-реквест, а не «заодно»
- [ ] Порядок правил не нарушен: запреты выше разрешений
- [ ] Последнее правило по-прежнему `DENY` для всего
- [ ] Табличные тесты политики дополнены случаями для нового правила
- [ ] Для нового опасного инструмента добавлен `CONFIRM` с описанием эффекта
- [ ] Условия проверяют нормализованные значения (`resolve()` для путей)

## 5. Контекст и память

- [ ] Изменение сборки окна не сливает `history` и окно
- [ ] Если добавлена статья контекста — у неё есть лимит в `ContextBudget`
- [ ] Если менялась компакция — валидатор потерь решений на месте
- [ ] Новый факт-источник имеет `source`, `confidence`, `ttl_days`, `verify`
- [ ] Данные из внешнего мира по-прежнему помечаются как недоверенные

## 6. Тесты

- [ ] У изменения есть тест, который **падает** без изменения (проверено локально)
- [ ] Если исправлен отказ — задача добавлена в golden set
- [ ] Если исправлена уязвимость — сценарий добавлен в набор инъекций
- [ ] Новые тесты не декоративны: попробуйте сломать код и убедитесь, что они краснеют
- [ ] Не добавлено тестов, которые не могут упасть (проверка вида `assert result is not None` после присваивания)

## 7. Наблюдаемость

- [ ] Новый код пишет спаны и структурные логи с полями из [10.4](../10-observability/#104-opentelemetry-для-агента-практическая-схема)
- [ ] Новое событие лога добавлено в закрытый список `event`
- [ ] Ошибка нового инструмента помечается `ERROR` на своём спане, а не на спане шага
- [ ] Ничего чувствительного не попало в атрибуты спанов и в логи

## 8. Стоимость

- [ ] Изменение не увеличивает постоянную часть окна незаметно
- [ ] Если добавлены схемы или справочные материалы — оценено влияние на `cost_per_success`
- [ ] Если добавлен вспомогательный вызов модели (критик, судья, компакция) — указано, какой моделью и как часто
- [ ] Кэш промптов по-прежнему попадает (`cached_tokens` не упал в дымовом прогоне)

---

## Красные флаги: не одобряйте, если

**Промпт меняется без чисел.** «Кажется, стало лучше» — не аргумент для системы, у которой есть golden set.

**Новый инструмент без `reject`-условий в наборе.** Вы не узнаете, если агент начнёт использовать его неправильно.

**Расширение прав в общем пулл-реквесте.** Такое изменение должно быть заметным, а не спрятанным среди рефакторинга.

**Тест, который не может упасть.** Это не защита, а иллюзия защиты, и она хуже отсутствия теста, потому что создаёт ложную уверенность.

**Правило безопасности только текстом.** Спросите: что произойдёт, если модель проигнорирует эту строку? Если ответ «плохое» — нужен исполняемый барьер.

---

## Как формулировать замечания

**Плохо:** «Мне кажется, описание можно улучшить».
**Хорошо:** «Описание `process_data` не отвечает на вопрос, когда его НЕ использовать; рядом есть `validate_data`, и модель будет их путать. Проверьте тестом описаний: 5 положительных и 5 отрицательных формулировок».

**Плохо:** «А это безопасно?»
**Хорошо:** «`send_report` — класс E по [2.10](../02-tool-calling/#210-опасные-инструменты-dry-run-подтверждение-откат): внешне видимое действие. Нужен `CONFIRM` с описанием эффекта и ключ идемпотентности. Плюс получатель должен браться из белого списка, а не из аргумента».

**Плохо:** «Нужны тесты».
**Хорошо:** «Добавьте задачу в `benchmarks/suites/main.yaml` с `reject` на изменение `tests/`. Проверьте, что она падает на текущей версии — иначе она ничего не проверяет».

Конкретика со ссылкой на раздел экономит цикл обсуждения и учит, а не просто блокирует.
