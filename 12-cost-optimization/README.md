## 12.1 Провал без этого модуля

**«Оптимизируем потом».** Прототип на десяти прогонах в день стоит копейки. При выходе на 50 000 прогонов в месяц выясняется, что цена одного результата 0,4 доллара, а продукт монетизируется на 0,1. Переделка архитектуры под экономику — это недели, и её делают под давлением, вместо того чтобы заложить с первого дня.

**Незаметная утечка.** Один инструмент начал возвращать больше данных после обновления зависимости. Расход вырос на 30% и остался незамеченным, потому что расходы не разбиты по инструментам и типам задач.

**Экономия, убившая качество.** Сократили контекст вдвое, счёт упал на 40%, pass rate упал на 15 процентных пунктов. Стоимость успешного результата при этом **выросла**: платим меньше за прогон, но успешных прогонов стало настолько меньше, что каждый успех стал дороже. Это главная ловушка модуля.

**Правило.** Оптимизируется не `cost_per_run`, а `cost_per_success`. Любая экономия, которую не проверили эвалами из [модуля 09](../09-evals/), — это не экономия, а гипотеза.

## 12.2 Откуда берутся деньги: анатомия счёта

Типовая структура расходов агентного прогона (порядок величин для многошаговых задач).

| Статья | Доля счёта | Почему столько | Основной рычаг |
|---|---|---|---|
| Входные токены — повторная отправка истории | 55–75% | История уходит заново на каждом шаге | Компакция, кэш, меньше шагов |
| Входные токены — схемы инструментов | 5–15% | Отправляются каждый шаг | Динамический набор |
| Входные токены — системный промпт | 3–8% | Каждый шаг | Кэш, сокращение |
| Входные токены — результаты инструментов | 5–20% | Необрезанные выводы | Обрезка, сводки, фильтр шума |
| Выходные токены | 5–15% | Дороже входных в 3–5 раз, но их мало | Краткие `thought`, структурированный вывод |
| Вспомогательные вызовы (компакция, критик, судья) | 5–15% | Отдельные вызовы модели | Дешёвая модель, реже |
| Эмбеддинги и реранк | менее 2% | Дёшево | Обычно не оптимизируется |

**Первый вывод.** Основные деньги — во входных токенах, а не в выходных. Интуиция «модель много пишет, поэтому дорого» неверна: агент много **читает**, причём одно и то же по многу раз.

**Второй вывод.** Оптимизация выходных токенов почти бессмысленна, за одним исключением: длинные `thought` на каждом шаге сначала платятся как выход, а потом ещё N раз как вход. Именно поэтому краткость рассуждений — не стилистика, а экономика.

**Как получить свою структуру.** Все нужные атрибуты уже есть, если сделан [модуль 10](../10-observability/): `llm.chat` с `in_tokens`, `out_tokens`, `cached_tokens`, `model`, плюс `context.build` с размерами по статьям. Один запрос по трейсам — и вы видите свою реальную раскладку. Делайте это до оптимизации: почти всегда обнаруживается, что главная статья не та, которую вы собирались оптимизировать.

## 12.3 Квадратичный рост и как его сломать

Формула из [модуля 01](../01-agent-basics/):

~~~
Входные токены ≈ N·(system + tools) + Σ(k=1..N) history_k
              ≈ N·B + Δ·N·(N+1)/2
~~~

где `N` — число шагов, `B` — постоянная часть (системный промпт плюс схемы), `Δ` — средний прирост истории за шаг.

**Числовой пример.** `B = 4500`, `Δ = 700`. При `N = 10`: 45 000 + 38 500 = 83 500. При `N = 20`: 90 000 + 147 000 = 237 000. При `N = 40`: 180 000 + 574 000 = 754 000. Удвоение числа шагов даёт примерно троекратный рост расходов, а не двукратный.

**Четыре способа сломать квадратичность, по силе.**

**1. Уменьшить `N`.** Самый мощный и самый недооценённый. Каждый лишний шаг стоит дороже предыдущего. Способы: лучшие описания инструментов (меньше ошибочных вызовов и повторов); параллельные вызовы; сводки вместо потоков (агенту не нужно три шага, чтобы понять результат тестов); подагент-исследователь вместо пяти шагов чтения.

**2. Ограничить `Δ`.** Обрезка выводов, фильтр шума, удаление `thought` закрытых шагов. Снижение `Δ` с 700 до 400 при `N = 20` даёт экономию около 35% всего счёта.

**3. Периодически сбрасывать историю.** Компакция превращает квадратичный рост в пилообразный: после каждого сжатия история начинается почти с нуля. Инкрементальная компакция каждые 5–8 шагов — практический оптимум.

**4. Уменьшить `B` через кэш.** Постоянная часть отправляется `N` раз; при кэшировании она стоит в 5–10 раз дешевле. См. 12.4.

**Комбинированный эффект.** На реальном прогоне из 30 шагов: сокращение до 22 шагов, `Δ` с 800 до 450, компакция каждые 6 шагов, кэш постоянной части. Итого снижение расходов в 3,5–4 раза при неизменном pass rate. Именно комбинация даёт эффект; каждый приём по отдельности даёт 20–40%.

## 12.4 Кэш промптов: самый выгодный приём

Провайдеры позволяют переиспользовать уже обработанный префикс запроса со скидкой (типично 75–90% от цены входа) и с заметным ускорением. Для агента это идеально: постоянная часть повторяется на каждом шаге.

**Условие работы кэша: стабильный префикс.** Кэш работает по совпадению начала запроса. Любое изменение в первых токенах обнуляет попадание.

**Правильный порядок сборки окна для кэша.**

~~~
[СТАБИЛЬНО, кэшируется]
1. Системный промпт (версионированный, не меняется в течение прогона)
2. Схемы инструментов (набор фиксирован на фазу)
3. Неизменные справочные материалы (глоссарий, правила проекта)
--- граница кэша ---
[ИЗМЕНЧИВО, не кэшируется]
4. Конспект и факты
5. Последние шаги
6. Результат последнего инструмента
7. Якорь: текущий пункт плана
~~~

**Пять правил, чтобы кэш реально попадал.**

1. **Никаких временных метк и `run_id` в начале.** Одна дата в системном промпте обнуляет кэш на всех прогонах. Если дата нужна, размещайте её после границы кэша.
2. **Стабильный порядок инструментов.** Сортируйте схемы по имени: множество в Python не гарантирует порядок, и вы получите разные префиксы на одинаковых наборах.
3. **Динамический набор инструментов меняйте по фазам, а не по шагам.** Каждая смена набора — промах кэша. Две-три фазы за прогон — нормально; смена на каждом шаге сводит выгоду к нулю.
4. **Не вставляйте персонализацию в начало.** Имя пользователя, идентификатор сессии — после границы.
5. **Измеряйте попадания.** Атрибут `cached_tokens` в `llm.chat`. Доля кэшированных входных токенов — метрика, которую надо вывести на дашборд. Ниже 50% на многошаговых прогонах означает, что префикс нестабилен.

~~~python
def build_cacheable_prefix(tools: ToolRegistry, phase: str) -> list[dict]:
    """Стабильная часть. Никаких дат, идентификаторов, случайностей."""
    return [
        {"role": "system", "content": SYSTEM_PROMPT_V14},        # версия в имени
        {"role": "system", "content": PROJECT_RULES},            # неизменно
        # схемы уходят отдельным полем API, но порядок фиксируем
    ], sorted(tools.for_phase(phase), key=lambda t: t["function"]["name"])
~~~

**Ожидаемый эффект.** На прогоне из 20 шагов с `B = 4500` постоянная часть даёт 90 000 входных токенов. При скидке 90% это эквивалентно 9 000 — экономия около 81 000 токенов, то есть примерно треть всего входного объёма типичного прогона. Один вечер работы, ощутимая экономия, нулевой риск для качества: содержимое контекста не меняется вообще.

## 12.5 Роутинг по сложности

Идея: дешёвая модель по умолчанию, дорогая — только там, где она нужна. Реализация проще, чем кажется, и эффект больше, чем кажется.

**Три стратегии роутинга.**

| Стратегия | Как решает | Плюсы | Минусы |
|---|---|---|---|
| По типу шага | Правила: исследование и парсинг — дешёвая; проектирование и синтез — дорогая | Просто, детерминированно, дёшево | Грубо |
| По результату | Начать дешёвой; при провале проверки — повторить дорогой | Платим за дорогую только когда нужно | Двойная работа на части задач |
| По классификатору | Отдельный дешёвый вызов оценивает сложность | Гибко | Ещё один вызов, ещё одна ошибка |

**Рекомендация: комбинация первых двух.** Правила по типу шага плюс эскалация при провале проверки. Классификатор добавляйте, только если измерили, что правил не хватает.

~~~python
CHEAP_STEPS = {"read", "search", "parse", "summarize", "classify", "extract"}
EXPENSIVE_STEPS = {"plan", "design", "synthesize", "critique", "resolve_conflict"}

def pick_model(step_kind: str, attempt: int, task_difficulty: int) -> str:
    if attempt > 1:
        return MODEL_STRONG            # эскалация после провала
    if step_kind in EXPENSIVE_STEPS or task_difficulty >= 4:
        return MODEL_STRONG
    return MODEL_CHEAP


def run_with_escalation(step, verify) -> Result:
    for attempt in (1, 2):
        model = pick_model(step.kind, attempt, step.difficulty)
        res = call(model, step)
        if verify(res).ok:
            return res
        log("router.escalated", from_model=model, step=step.kind)
    return res                          # вернуть с пометкой «не верифицировано»
~~~

**Важная деталь: эскалация требует проверки.** Без машинной проверки результата эскалация невозможна — вы не знаете, что дешёвая модель не справилась. Поэтому роутинг практически бесполезен без [модуля 09](../09-evals/): сначала критерии, потом экономия.

**Реалистичные ожидания.** На типичной смеси шагов 60–75% приходится на «дешёвые» типы. При разнице цен в 15–20 раз это даёт экономию 50–65% при эскалации в 10–20% случаев. Проверять обязательно на своём наборе: если эскалаций больше 30%, роутинг не экономит, а добавляет работу.

**Чего не делать.** Не роутить по длине запроса (не коррелирует со сложностью). Не роутить случайно «для A/B» без фиксации в трейсе — потом невозможно разобрать провал. Не менять модель посреди шага: контекст и кэш привязаны к модели.

## 12.6 Двенадцать приёмов экономии по эффективности

Отсортированы по отношению «экономия на час работы». Внедряйте сверху вниз.

| № | Приём | Типичная экономия | Риск для качества | Работы |
|---|---|---|---|---|
| 1 | Кэш промптов (стабильный префикс) | 25–40% | Нулевой | Вечер |
| 2 | Обрезка выводов инструментов с флагом | 10–25% | Низкий: нужен честный флаг и подсказка | Час |
| 3 | Фильтр шума в выводах (ANSI, прогресс-бары, префиксы логов) | 5–15% | Нулевой | Час |
| 4 | Инкрементальная компакция каждые 5–8 шагов | 20–35% на длинных прогонах | Средний: нужен валидатор потерь | День |
| 5 | Динамический набор инструментов по фазам | 5–15% | Низкий | Полдня |
| 6 | Роутинг по типу шага с эскалацией | 30–60% | Средний: обязательны проверки | 1–2 дня |
| 7 | Сводки вместо потоков (тесты, сборка, логи) | 10–20% плюс меньше шагов | Низкий | Полдня |
| 8 | Краткие `thought` (1–3 предложения) и удаление `thought` закрытых шагов | 5–12% | Низкий | Час |
| 9 | Подагент-исследователь вместо больших чтений | 10–30% на исследовательских задачах | Средний | 1–2 дня |
| 10 | Кэш результатов инструментов внутри прогона | 3–10% | Нулевой | Полдня |
| 11 | Батчевая обработка независимых задач через асинхронный режим провайдера | до 50% на офлайн-нагрузке | Нулевой (растёт задержка) | День |
| 12 | Переход с агента на workflow там, где путь известен | 60–90% на этом классе задач | Нулевой при верной классификации | Зависит |

**Про приём 12 отдельно.** Самая большая экономия в агентных системах — это не оптимизация агента, а обнаружение задач, которым агент не нужен. Пройдите тест из [раздела 1.10](../01-agent-basics/) по вашим реальным типам задач. Если 40% нагрузки решается фиксированной цепочкой, вы можете снизить общий счёт вдвое, ничего не оптимизируя.

**Про приём 11.** Асинхронные (батчевые) режимы провайдеров дают скидку за то, что результат придёт не сразу. Для интерактивных сценариев не подходит, для ночной обработки, переиндексации, массовых эвалов — идеально. Часто забывают, что эвалы можно гонять батчем: это снижает стоимость измерений в разы.

**Чего в списке нет и почему.** Дистилляция и файнтюн: дают экономию, но требуют данных, инфраструктуры и переобучения при каждом изменении задачи; рассматривайте после того, как исчерпаны первые 12. Сжатие контекста нейросетевыми методами: сложно, риск потери смысла, выгода меньше, чем от честной компакции. Самописные кэши эмбеддингов: эмбеддинги и так дёшевы, экономия незаметна.

## 12.7 Бюджеты, лимиты и деградация

**Три уровня бюджета.**

| Уровень | Лимит | Что происходит при исчерпании |
|---|---|---|
| Прогон | `max_cost_usd` из [модуля 01](../01-agent-basics/) | Мягкое предупреждение на 80%, безопасное завершение на 100% |
| Пользователь или задача-тип | Квота в сутки | Деградация: дешёвая модель, меньше шагов, отказ от опциональных вызовов |
| Организация | Дневной и месячный потолок | Приостановка неинтерактивных прогонов, алерт |

**Деградация вместо отказа.** Правильная реакция на исчерпание квоты — не «сервис недоступен», а осознанное снижение возможностей.

~~~python
@dataclass
class DegradationLevel:
    name: str
    model: str
    max_steps: int
    enable_critic: bool
    enable_rag: bool
    rag_top_k: int

LEVELS = [
    DegradationLevel("full",     MODEL_STRONG, 24, True,  True,  6),
    DegradationLevel("reduced",  MODEL_CHEAP,  16, True,  True,  4),
    DegradationLevel("minimal",  MODEL_CHEAP,  10, False, True,  3),
    DegradationLevel("last",     MODEL_CHEAP,   6, False, False, 0),
]

def pick_level(spent_ratio: float) -> DegradationLevel:
    if spent_ratio < 0.7:  return LEVELS[0]
    if spent_ratio < 0.9:  return LEVELS[1]
    if spent_ratio < 1.0:  return LEVELS[2]
    return LEVELS[3]
~~~

**Важное свойство.** Уровень деградации записывается в трейс и в ответ пользователю («работал в сокращённом режиме»). Иначе вы получите загадочное падение качества в конце каждого месяца, которое никто не сможет объяснить.

**Автомат отключения для внешних вызовов.** Если провайдер отвечает ошибками, не нужно повторять 300 раз: после N ошибок за окно переключиться на резервную модель или остановить неинтерактивные прогоны на T минут. Это защита не только от расходов, но и от каскадных отказов.

**Проверка лимита перед тратой, а не после.** Повторим из [модуля 01](../01-agent-basics/): `budget.exceeded()` вызывается до `llm.chat`. Очевидно, и постоянно нарушается.

## 12.8 Учёт: атрибуция расходов

Нельзя оптимизировать то, что не разбито по осям.

**Обязательные оси атрибуции.** Тип задачи (категория из golden set). Пользователь или тенант. Версия промптов. Модель. Стадия прогона (планирование, исследование, изменение, проверка, компакция, критик). Исход (`done`, `failed` и так далее).

**Ключевой отчёт: стоимость по типу задачи и исходу.**

~~~
Тип задачи      Прогонов  Успех  cost/run  cost/success  Δ к прошлой нед.
bugfix              1240   0.78     0.031        0.040          -6%
feature              310   0.61     0.078        0.128         +14%
investigation        890   0.74     0.024        0.032           0%
refactor             210   0.66     0.095        0.144          -3%
итого               2650   0.74     0.038        0.051          -2%
~~~

**Что видно из такого отчёта и не видно из общего счёта.** `feature` дороже `bugfix` втрое по успешному результату и растёт — там и надо копать. `investigation` дёшев и стабилен — его оптимизировать бессмысленно. Общая цифра «-2%» скрывает рост в самой дорогой категории.

**Отчёт по стадиям.** Вторая по полезности разбивка: сколько уходит на планирование, на исследование, на изменение, на проверку, на компакцию, на критика. Типичное открытие: вспомогательные вызовы (компакция плюс критик плюс судья) составляют 20–25% счёта, хотя их «как бы нет» в интуитивной модели.

**Правило свежести.** Отчёт смотрится раз в неделю. Ежедневно — только алерт на всплеск. Ежемесячно — уже поздно: за месяц утечка успевает стоить.

## 12.9 Как это ломается: девять ошибок

**1. Оптимизация `cost_per_run` вместо `cost_per_success`.** Признак: счёт упал, жалобы выросли. Лечение: считать `cost_per_success` и проверять эвалами.

**2. Нестабильный префикс.** Признак: `cached_tokens` близко к нулю. Лечение: убрать даты и идентификаторы из начала, зафиксировать порядок схем.

**3. Смена набора инструментов на каждом шаге.** Признак: кэш не попадает при «динамическом наборе». Лечение: менять набор по фазам, 2–3 раза за прогон.

**4. Компакция только на пороге.** Признак: пилообразные расходы с высокими пиками. Лечение: инкрементально каждые 5–8 шагов.

**5. Молчаливая обрезка.** Признак: экономия есть, качество упало необъяснимо. Лечение: флаг `truncated` и подсказка в тексте результата.

**6. Роутинг без проверок.** Признак: дешёвая модель отвечает хуже, эскалации не происходит. Лечение: машинные критерии, затем роутинг.

**7. Нет атрибуции.** Признак: «счёт вырос», причина неизвестна. Лечение: оси из 12.8.

**8. Лимит проверяется после вызова.** Признак: перерасход ровно на один дорогой шаг регулярно. Лечение: проверка до траты.

**9. Отказ вместо деградации.** Признак: в конце месяца сервис отвечает «недоступно». Лечение: уровни деградации с пометкой в ответе.

## Упражнения

<details>
<summary><b>Задача 1.</b> Посчитайте эффект кэша</summary>

`B` (системный промпт плюс схемы) = 5 000 токенов, `N` = 18 шагов, `Δ` = 600. Цена входа 0,20 доллара за миллион, кэшированный вход — 0,02. Сколько экономит кэш и какова его доля в общем счёте входа?

**Ответ.** Постоянная часть: 18 × 5 000 = 90 000 токенов. История: 600 × 18 × 19 / 2 = 102 600. Всего входа 192 600. Без кэша: 192 600 / 1e6 × 0,20 = 0,0385 доллара. С кэшем на постоянной части: 90 000 × 0,02 / 1e6 = 0,0018 плюс 102 600 × 0,20 / 1e6 = 0,0205, итого 0,0223. Экономия 42% входных расходов при нулевом изменении содержимого контекста. Доля постоянной части до кэша была 47% — именно поэтому приём стоит первым в таблице 12.6.
</details>

<details>
<summary><b>Задача 2.</b> Найдите ловушку экономии</summary>

Внедрили сокращение контекста: убрали конспект и факты из окна. `cost_per_run` упал с 0,040 до 0,024 (−40%). pass rate упал с 0,74 до 0,58. Хорошая оптимизация?

**Ответ.** Нет, катастрофическая. `cost_per_success` до: 0,040 / 0,74 = 0,054. После: 0,024 / 0,58 = 0,041 — на первый взгляд лучше. Но нужно учесть, что неуспешные прогоны требуют повторов или ручной работы: если считать полную стоимость получения результата (включая повторный прогон при провале), картина меняется. Проверка: ожидаемое число прогонов до успеха 1/0,74 = 1,35 против 1/0,58 = 1,72; стоимость получения результата 0,040×1,35 = 0,054 против 0,024×1,72 = 0,041. Формально дешевле, но: выросла задержка получения результата, выросла нагрузка на людей, и падение на 16 пунктов почти наверняка вышло за интервал. Правильный вывод: экономия достигнута не тем способом. Убирать конспект нельзя; вместо этого сжать его сильнее, вынести факты в отбор по релевантности, включить кэш. Мораль: даже когда `cost_per_success` формально улучшается, проверяйте, чем именно вы заплатили.
</details>

<details>
<summary><b>Задача 3.</b> Спроектируйте роутинг</summary>

Смесь: 55% шагов — чтение и поиск, 20% — парсинг результатов, 15% — планирование и синтез, 10% — критика. Дешёвая модель в 18 раз дешевле. Оцените экономию при 15% эскалаций.

**Ответ.** «Дешёвые» типы: 55 + 20 = 75% шагов. Из них 15% эскалируются, то есть выполняются дважды (дешёвая плюс дорогая). Пусть цена дорогой = 18, дешёвой = 1. Базовый вариант (всё дорогой): 100 × 18 = 1800 условных единиц. С роутингом: дорогие типы 25 × 18 = 450; дешёвые 75 шагов: 75 × 1 = 75, плюс эскалации 0,15 × 75 × 18 = 202,5. Итого 727,5. Экономия примерно 60%. Порог безубыточности: эскалация становится невыгодной при доле выше примерно 94% — то есть роутинг с эскалацией почти всегда выгоден по деньгам. Настоящее ограничение — не деньги, а задержка: эскалация удваивает время на 15% шагов.
</details>

<details>
<summary><b>Задача 4.</b> Разберите всплеск расходов</summary>

Расходы выросли на 60% за неделю. Изменений в промптах не было. Какие пять гипотез проверить по трейсам и в каком порядке?

**Ответ.** По порядку дешевизны проверки: (1) `cached_tokens` упал — что-то нарушило стабильность префикса (обновление библиотеки, порядок схем, добавленная дата); (2) вырос `bytes_out` у какого-то инструмента — обновление зависимости стало возвращать больше данных; (3) вырос средний `N` — агент делает больше шагов, возможно из-за роста доли повторов или ошибок инструментов; (4) изменилось распределение по `model` — роутер чаще уходит на дорогую, значит выросла доля провалов проверок; (5) сместилось распределение типов задач — больше `feature`, которые дороже. Все пять проверяются одним запросом по атрибутам из [модуля 10](../10-observability/), сравнением двух недель. Без атрибуции пришлось бы гадать; с ней — 15 минут.
</details>

<details>
<summary><b>Задача 5.</b> Спроектируйте деградацию</summary>

Дневная квота тенанта исчерпана на 85%. Опишите, что именно отключается, и что видит пользователь.

**Ответ.** Уровень `reduced`: модель дешёвая; `max_steps` с 24 до 16; `rag_top_k` с 6 до 4; критик остаётся (он дешёвый и защищает качество); подагенты-исследователи остаются (они экономят); отключается второй цикл критики и опциональная перепроверка. Пользователь видит явную пометку в ответе: «выполнено в сокращённом режиме из-за исчерпания дневной квоты; полный режим восстановится в 00:00 UTC» плюс, если применимо, предложение поставить задачу в ночную очередь с батчевой обработкой (дешевле и без ограничений). Уровень пишется в трейс, чтобы падение качества в отчётах было объяснимо. Чего не делать: молча снижать качество и молча отказывать.
</details>

<details>
<summary><b>Задача 6.</b> Антиметрика экономии</summary>

Метрика: «стоимость прогона снижена на 45% за квартал». Какие три антиметрики обязательны?

**Ответ.** (1) pass rate по всем категориям и особенно по `difficulty 4–5`: экономия часто достигается за счёт сложных задач. (2) `cost_per_success`: главное число, оно может вырасти при падении `cost_per_run`. (3) Доля прогонов, выполненных в деградированном режиме: если она выросла с 2% до 30%, «экономия» — это просто хроническое исчерпание квот. Четвёртая полезная: доля `done_unverified` — экономия за счёт отключения проверок выглядит как экономия только до первого инцидента. Отчёт об экономии без этих чисел не следует принимать.
</details>

## Чек-лист приёмки модуля

- [ ] Известна структура расходов по статьям из 12.2, посчитанная по своим трейсам
- [ ] Главная метрика — `cost_per_success`, а не `cost_per_run`
- [ ] Кэш промптов работает; `cached_tokens` на дашборде; доля выше 50% на многошаговых прогонах
- [ ] Префикс стабилен: нет дат и идентификаторов в начале, порядок схем зафиксирован
- [ ] Набор инструментов меняется по фазам, а не по шагам
- [ ] Выводы инструментов обрезаются с флагом и подсказкой; работает фильтр шума
- [ ] Компакция инкрементальная, каждые 5–8 шагов
- [ ] `thought` ограничены по длине; `thought` закрытых шагов удаляются при компакции
- [ ] Роутинг по типу шага с эскалацией; доля эскалаций измерена и ниже 30%
- [ ] Есть кэш результатов инструментов внутри прогона
- [ ] Офлайн-нагрузка (эвалы, переиндексация) идёт батчевым режимом
- [ ] Проведена ревизия: какие типы задач можно перевести с агента на workflow
- [ ] Бюджеты трёх уровней; проверка до траты; мягкий порог 80%
- [ ] Реализованы уровни деградации; уровень пишется в трейс и сообщается пользователю
- [ ] Есть автомат отключения на ошибки провайдера
- [ ] Расходы атрибутированы по типу задачи, модели, стадии, версии промптов и исходу
- [ ] Недельный отчёт по `cost_per_success` в разрезе типов задач; алерт на всплеск

**Антиметрика модуля.** Если ваша экономия не проверена прогоном golden set, это не экономия, а гипотеза. Правило: любое изменение, снижающее расходы, идёт в одном коммите с результатами эвалов до и после. Коммит «оптимизация контекста» без чисел по pass rate — кандидат на откат.
